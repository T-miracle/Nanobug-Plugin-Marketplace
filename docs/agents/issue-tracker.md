# 议题跟踪器

仓库：[T-miracle/Nanobug-Plugin-Marketplace](https://github.com/T-miracle/Nanobug-Plugin-Marketplace)。

2026-10-09 用户批准四张粗粒度工单及直接阻塞边，并要求在独立市场仓库发布方案与工单。原 [Nanobug #100](https://github.com/T-miracle/Nanobug/issues/100) 保留历史，本仓库议题承载后续执行。

## 发布与幂等

- 方案与每张工单分别创建 issue，保留完整正文，统一 ready-for-agent，不额外分诊或指派。
- 发布前查询正文稳定标识及[发布记录](../tickets/publication.json)，未知结果先读回再重试。
- 按阻塞项优先发布；正文使用真实链接，原生依赖使用数据库 issue ID，不把编号当作 ID。
- 发布后读回正文、状态、标签及阻塞边，保存返回标识。只有原生关系确实不可用才保留正文回退并说明限制。
- 父规格是依据，不是必须先关闭的阻塞项；不改写或关闭父规格推进子工单。

## 授权与执行

- 本次授权包括创建公开项目仓库、迁入方案/工单、编写规范、普通提交推送和发布议题。尚未授权开始功能实现、发布插件或开启 Pages 服务。
- 用户后续要求执行工单时，先明确其已有授权与所涉仓库规则；验证通过前不关闭。需要提交/推送时先检查只包含本工单改动，推送后核对远程再读回议题状态。
- 不强制推送、历史重写或夹带其他仓库未提交改动；不同仓库分别记录提交与交付证据。
- 开始工单只要求其真实直接前置完成；并行关系不代表并行代理已获授权。
- 优先用 GitHub 连接器；能力或权限缺失时可用用户已有 Git 认证调用 GitHub API。凭据不打印、不写入文件或议题。

## 两种 PR

本项目实施请求通过 issue 跟踪；第三方插件收录通过注册表 PR 审核。这两者职责不同。首次收录、每个新版本和归属转移遵循执行规格。
